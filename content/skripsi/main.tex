\abstractind
Skripsi ini membandingkan dua mode pengelolaan konfigurasi pada satu stack InvenioRDM produksi-like: mode imperatif terotomasi berbasis \texttt{kubectl} dan mode GitOps berbasis ArgoCD. Pada mode imperatif, \textit{auto-sync}/\textit{self-heal} ArgoCD dijeda, pemeriksa dan \textit{runbook} otomatis menjalankan koreksi \texttt{kubectl}, lalu ArgoCD dipulihkan; ini bukan \textit{deployment} terpisah dan bukan studi waktu reaksi manusia. Kedua mode berjalan berurutan pada stack yang sama, dengan tujuh skenario \textit{drift} dan lima belas pengulangan per skenario per mode, sehingga total 210 sel. Apparatus dibekukan sebelum pengumpulan pada revisi sumber \texttt{81ddd25}, SHA-256 render \texttt{a5efd711}, dan \textit{image digest} tetap.

Dari 210 sel, 207 baris dianalisis dan empat dikecualikan sebagai kegagalan instrumentasi serta lingkungan yang dilaporkan terbuka. Pada RQ1, kedua mode mengembalikan skor kesetaraan bidang terpilih ke keadaan yang dideklarasikan pada skenario A--F; skenario G merupakan satu-satunya asimetri karena mode GitOps tidak mengembalikan anotasi di luar himpunan bidang yang dikelolanya. Pada RQ2, seluruh dua belas perbandingan B--E menolak hipotesis nol setelah koreksi Holm, tetapi selisih waktu deteksi sekitar empat detik bersesuaian dengan interval \textit{polling} pemeriksa imperatif, sehingga perbedaan tersebut terutama mencerminkan mekanisme pengamatan. Ukuran efek pemulihan jauh lebih kecil ($\delta = 0{,}48$ untuk B dan $0{,}75$ untuk C) daripada deteksi, sehingga keunggulan waktu terkonsentrasi di awal siklus rekonsiliasi dan menyusut di akhir.

R3 tidak diukur karena audit API server tidak tersedia. Penelitian ini merupakan studi kasus eksploratif pada satu klaster dengan mode berurutan, sehingga tidak menyimpulkan keunggulan umum salah satu mode, tidak menyimpulkan kelayakan adopsi, dan tidak membuktikan kebenaran semantik konfigurasi yang dideklarasikan.

\vspace{0.5cm}
\noindent\textbf{Kata Kunci:} penyimpangan konfigurasi, Kubernetes, GitOps, otomasi imperatif, studi kasus komparatif terkontrol
\endabstractind

\abstracteng
This thesis compares two configuration-management modes on one production-like InvenioRDM stack: an automated imperative mode based on \texttt{kubectl} and a GitOps mode based on ArgoCD. In the imperative mode, ArgoCD auto-sync/self-heal is paused, an automated checker and runbook perform \texttt{kubectl} corrections, and ArgoCD is then restored; this is neither a separate deployment nor a human-reaction-time study. Both modes run sequentially on the same stack across seven drift scenarios with fifteen repetitions per scenario per mode, totalling 210 cells. The apparatus was frozen before collection at source revision \texttt{81ddd25}, render SHA-256 \texttt{a5efd711}, and a fixed image digest.

Of the 210 cells, 207 rows were analysed and four were excluded as openly reported instrumentation and environmental failures. For RQ1, both modes returned the selected-field equality score to the declared state for scenarios A--F; scenario G is the sole asymmetry because the GitOps mode did not revert an annotation outside its managed field set. For RQ2, all twelve B--E comparisons rejected the null after Holm correction, but the roughly four-second detection gap matches the imperative checker polling interval, so that difference mainly reflects the observation mechanism. Recovery effect sizes are materially smaller ($\delta = 0.48$ for B and $0.75$ for C) than detection, so the timing advantage is concentrated at the start of the reconciliation cycle and shrinks at the end.

R3 was not measured because Kubernetes API-server audit was unavailable. This is an exploratory single-case study on one cluster with sequential arms; it therefore claims neither general superiority of either mode, nor adoption suitability, nor semantic correctness of the declared configuration.

\vspace{0.5cm}
\noindent\textbf{Keywords:} configuration drift, Kubernetes, GitOps, automated imperative management, controlled single-case comparative study
\endabstracteng
