\abstractind
Skripsi ini merancang studi kasus komparatif terkontrol atas dua mode pengelolaan pada satu stack InvenioRDM produksi-like: mode imperatif terotomasi berbasis \texttt{kubectl} dan mode GitOps berbasis ArgoCD. Pada mode imperatif, \textit{auto-sync}/\textit{self-heal} ArgoCD dijeda, pemeriksa dan \textit{runbook} otomatis menjalankan koreksi \texttt{kubectl}, lalu ArgoCD dipulihkan; ini bukan \textit{deployment} terpisah dan bukan studi waktu reaksi manusia. Kedua mode berjalan berurutan pada stack yang sama; tidak ada stack kembar \texttt{exp-*} dan tidak ada eksekusi paralel A/B, sehingga non-isolasi terhadap beban latar dan dependensi bersama menjadi keterbatasan eksplisit. HPA normal dipertahankan pada kedua mode, sehingga skenario A menjadi kontrol HPA dan \texttt{/spec/replicas} dikecualikan dari R1 statis; skenario F diperlakukan terpisah sebagai batas visibilitas sumber daya di luar cakupan aplikasi; skenario G adalah kasus deskriptif yang bukan \textit{self-heal} ArgoCD. Metrik yang dirancang mencakup kesetaraan bidang konfigurasi dan kesehatan secara terpisah (R1), waktu deteksi, waktu ketersediaan bukti penyimpangan, dan waktu pemulihan konfigurasi penuh (R2). R3 tidak diukur karena audit API server tidak tersedia dan tidak dilaporkan sebagai nol atau tidak ada perbedaan. Sampel formal adalah $7 \times 2 \times 15 = 210$ run (10 R2 dan 5 R1 per sel) dengan sampling satu detik serta pembekuan revisi sumber, render, image digest, dan versi runtime. Protokol dan apparatus masih menunggu tinjauan serta validasi, dan data formal belum tersedia. Oleh sebab itu, skripsi ini belum melaporkan hasil komparatif atau kesimpulan empiris.

\vspace{0.5cm}
\noindent\textbf{Kata Kunci:} penyimpangan konfigurasi, Kubernetes, GitOps, otomasi imperatif, studi kasus komparatif terkontrol
\endabstractind

\abstracteng
This thesis designs a controlled single-case comparative study of two management modes on one production-like InvenioRDM stack: an automated imperative mode based on \texttt{kubectl} and a GitOps mode based on ArgoCD. In the imperative mode, ArgoCD auto-sync/self-heal is paused, an automated checker and runbook perform \texttt{kubectl} corrections, and ArgoCD is then restored; this is not a separate deployment and not a human-reaction-time study. Both modes run sequentially on the same stack; there is no \texttt{exp-*} twin and no parallel A/B execution, so non-isolation from background load and shared dependencies is an explicit limitation. Normal HPA operation is retained in both modes, so scenario A is an HPA control and \texttt{/spec/replicas} is excluded from static R1; scenario F is a visibility-boundary case for resources outside the application scope; scenario G is a descriptive case that is not an ArgoCD self-heal case. The measures comprise configuration-field equality and health reported separately (R1), time to detection, availability of verifiable deviation evidence, and full configuration restoration (R2). R3 is not measured because Kubernetes API-server audit is unavailable and is not reported as zero or as no difference. The formal sample is 7 x 2 x 15 = 210 runs (10 R2 and 5 R1 per cell) with one-second sampling and frozen source revision, render, image digests, and runtime versions. The protocol and apparatus remain subject to review and validation, and no formal dataset is available. Accordingly, no comparative findings or empirical conclusions are reported in this draft.

\vspace{0.5cm}
\noindent\textbf{Keywords:} configuration drift, Kubernetes, GitOps, automated imperative management, controlled single-case comparative study
\endabstracteng
